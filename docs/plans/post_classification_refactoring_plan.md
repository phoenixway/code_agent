# План рефакторингу для `_run_post_classification_stage`

## Загальний огляд архітектури

Система обробки відповідей моделі побудована на концепції **фазово-орієнтованого конвеєра (phase-ordered pipeline)**, що є чудовим архітектурним рішенням. Центральний клас `ModelResponsePipeline` діє як координатор, делегуючи роботу спеціалізованим обробникам, що реалізовані як міксини (`ResponsePipelinePrevalidationMixin`, `ResponsePipelineStagesMixin`). Це забезпечує чіткий розподіл відповідальності на високому рівні.

Порядок етапів (валідація, чекпоінт, класифікація) є фіксованим і критично важливим для коректності, що обґрунтовує відмову від більш гнучких, але менш безпечних патернів, як "Ланцюжок обов'язків".

## Виявлена проблема: Архітектурна деградація в `_run_post_classification_stage`

Головна проблема полягає в методі `_run_post_classification_stage` у файлі `modules/agent/orchestration/responses/response_pipeline_stages.py`. Цей метод, по суті, перетворився на другий "великий процедурний згусток", що суперечить початковим цілям архітектури.

**Аналіз проблеми:**

1.  **Змішування відповідальностей**: Цей метод змішує в собі логіку, яка мала б бути ізольованою:
    *   **Відновлення після помилок (Recovery)**: Виклик `self.output_recovery.decide()`.
    *   **Застосування політик (Policy)**: Виклик `self.action_policy.decide()`.
    *   **Спеціалізовані перевірки (Guards)**: Велика кількість `if-elif-else` блоків для обробки специфічних випадків (`reflection_repair_pending`, `force_plaintext_completion`, `multiple_actions` тощо).

2.  **Висока складність**: Через велику кількість умовних переходів та вкладеність логіки, метод стає важким для розуміння, модифікації та тестування. Будь-яка зміна може мати непередбачувані наслідки для інших частин конвеєра.

3.  **Порушення фазової архітектури**: Замість того, щоб бути окремими, чітко визначеними фазами, логіка відновлення та застосування політик виявилася "розмазаною" всередині одного великого методу.

## Пропозиція щодо рефакторингу

Пропоную провести рефакторинг `_run_post_classification_stage`, виділивши з нього логіку в окремі, незалежні обробники (етапи), аналогічно до того, як це вже зроблено для `_run_initial_stages` та `_run_checkpoint_stage`.

**Крок 1: Виділити `OutputRecoveryStage`**

Створити новий метод (або навіть окремий клас/міксин), який буде відповідати виключно за логіку відновлення.

*   **Вхід**: `ClassifiedStageState` (результат попереднього етапу).
*   **Логіка**: Інкапсулює `await self.output_recovery.decide(...)` та пов'язані з ним перевірки.
*   **Вихід**: Новий об'єкт стану `RecoveryStageOutcome`, який містить рішення про відновлення (продовжити з новим запитом, зупинитись, або передати далі).

**Крок 2: Виділити `ActionPolicyStage`**

Створити етап для застосування політик до дій.

*   **Вхід**: Результат попереднього етапу (після відновлення).
*   **Логіка**: Інкапсулює `await self.action_policy.decide(...)` та перевірку на множинні дії.
*   **Вихід**: `ActionPolicyOutcome`, що містить рішення (продовжити, відхилити, відправити на виконання).

**Крок 3: Оновити `_run_post_classification_stage`**

Після рефакторингу цей метод має стати значно простішим і лише координувати виклики нових етапів.

**Приклад (псевдокод):**

```python
# У ResponsePipelineStagesMixin

async def _run_post_classification_stage(self, ctx, classified):
    # Етап 1: Застосування спеціальних охоронців (Guards)
    guard_outcome = await self._run_post_classification_guards(ctx, classified)
    if guard_outcome.should_stop():
        return guard_outcome

    # Етап 2: Відновлення після помилок
    recovery_outcome = await self._run_recovery_stage(ctx, guard_outcome)
    if recovery_outcome.should_stop():
        return recovery_outcome

    # Етап 3: Застосування політик дій
    policy_outcome = await self._run_action_policy_stage(ctx, recovery_outcome)
    if policy_outcome.should_stop():
        return policy_outcome

    # Етап 4: Фінальне рішення про відправку
    return self._prepare_dispatch_ready(policy_outcome)
```

### Переваги пропонованого рефакторингу

1.  **Відновлення архітектурної цілісності**: Повернення до чіткого фазово-орієнтованого підходу.
2.  **Зниження складності**: Кожен етап буде простим, зрозумілим і матиме одну відповідальність (Single Responsibility Principle).
3.  **Покращення тестування**: Маленькі, сфокусовані методи набагато легше тестувати ізольовано.
4.  **Спрощення подальших модифікацій**: Додавання нових правил чи політик не вимагатиме зміни складного монолітного методу.
