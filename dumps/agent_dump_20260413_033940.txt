* точнішої валідації `list_directory`
* більш розумного пріоритету інструментів на старті дослідження

## Завдання 1. Оновити системний prompt

Файл: `modules/defaults.py`

### Потрібна нова поведінка

Для задач типу:

* огляд проекту
* аналіз архітектури
* дослідження структури репозиторію
* огляд Kotlin/Gradle проекту
* огляд Python проекту

агент має **спочатку** використовувати таку стратегію:

### Для Kotlin / Android / KMP / Gradle проектів

1. `read_file settings.gradle.kts` або `settings.gradle`
2. `read_file build.gradle.kts` або `build.gradle`
3. `search_files` для ключових слів:

   * `desktop`
   * `shared`
   * `app`
   * `domain`
   * `data`
   * `navigation`
   * `repository`
   * `usecase`
4. `search_content` для ключових маркерів:

   * `@Composable`
   * `RoomDatabase`
   * `Repository`
   * `UseCase`
   * `NavHost`
   * `Desktop`
   * `expect` / `actual`
5. Лише після цього точковий `list_directory` для 2-3 конкретних директорій

### Для Python проектів

1. `read_file pyproject.toml`, `requirements.txt`, `setup.py`, `Pipfile` або `poetry.lock` якщо існують
2. `search_files` для ключових слів:

   * `app`
   * `core`
   * `api`
   * `models`
   * `services`
   * `tests`
   * `cli`
   * `main`
3. `search_content` для ключових маркерів:

   * `FastAPI`
   * `Flask`
   * `Django`
   * `Typer`
   * `click`
   * `BaseModel`
   * `SQLAlchemy`
   * `pytest`
4. Лише після цього точковий `list_directory`

### Явно додати в prompt правило

Для repository inspection:

* do not begin with deep directory-by-directory traversal
* prefer config/build file reads first
* then file/content search
* use `list_directory` only for targeted confirmation
* avoid repeated root-level directory listing
* if `list_directory` is used in a batch, every item must include an explicit `path`

### Особливо важливо

У prompt прямо дописати змістом таке:

* for Kotlin/Gradle projects, inspect `settings.gradle(.kts)` and build files before broad directory traversal
* for Python projects, inspect `pyproject.toml` / `requirements.txt` / `setup.py` before broad traversal
* prefer `search_files` and `search_content` over repeated nested `list_directory`
* repeated root traversal is low-value and should be avoided

## Завдання 2. Оновити recovery prompts для multi-file investigation

Файл: `orchestrator.py`

### Потрібна нова поведінка

Коли агент входить у режим recovery після серії single read-only actions або при ознаках неефективного multi-file investigation, recovery prompt має не просто казати:

* “return a compact batch”

а ще й **вказувати правильний пріоритет інструментів**.

### Новий зміст recovery prompt

Для випадків на кшталт:

* repeated single read-only actions
* multi-file investigation stagnation
* repeated root/directory exploration

recovery має інструктувати приблизно так за змістом:

* Stop deep directory-by-directory traversal.
* For project inspection, first read project config/build entry files.
* Then use `search_files` and `search_content` to locate relevant modules.
* Use `list_directory` only for specific target directories.
* If batching `list_directory`, every action must include an explicit `path`.
* Prefer high-information actions over repeated root exploration.

### Для Kotlin проектів recovery має підказувати

* `settings.gradle.kts`
* `build.gradle.kts`
* `search_files` for shared / desktop / app / domain / data
* `search_content` for Compose / Room / Repository / UseCase / Nav

### Для Python проектів recovery має підказувати

* `pyproject.toml`
* `requirements.txt`
* `setup.py`
* `search_files` for app / api / models / services / tests
* `search_content` for FastAPI / Flask / Django / SQLAlchemy / pytest

## Завдання 3. Додати жорстку валідацію `list_directory` payload

Файли:

* `action_dispatcher.py`
* за потреби `processor.py`

### Потрібна нова поведінка

`list_directory` без явного `path` не повинен просто виконуватись із fallback на root у випадках project investigation batch.

Потрібно:

1. перевіряти `list_directory` payload перед виконанням
2. якщо `path` відсутній або порожній:

   * не викликати інструмент
   * повертати точний recoverable error
   * пояснювати, що для `list_directory` потрібен explicit `path`
   * у batched read-only investigation забороняти “мовчазний root fallback”

### Очікуваний текст помилки

Щось близьке за змістом:

* Invalid `list_directory` payload: explicit `path` is required.
* Do not omit `path` in read-only batches.
* Root listing without intent is blocked because it causes low-value repeated exploration.

### Важливо

Це має бути **валідація payload**, а не просто UI warning.

## Завдання 4. Вбудувати heuristic для пріоритету search over directory walk

Файли:

* `state_machine.py`
* `policy_engine.py`
* за потреби `orchestrator.py`

### Потрібна нова поведінка

Коли `start_turn()` бачить, що користувач просить:

* проаналізувати проект
* зробити огляд додатку
* оцінити архітектуру
* дати рекомендації по репозиторію
* дослідити desktop/shared/python structure

система повинна вважати це **project inspection mode**.

У цьому режимі:

* повторні `list_directory` мають швидше вважатися stagnation
* repeated root-level exploration має блокуватися раніше
* `search_files` і `search_content` мають вважатися кращим recovery path
* `read_file` для build/config files має мати високий пріоритет

### Бажане рішення

Додати окремий lightweight signal, наприклад:

* `project_inspection_mode: bool`

Його можна вмикати за ключовими словами в user input:

* Kotlin, Android, desktop, Compose, Gradle, shared, architecture, project, repo, repository
* Python, FastAPI, Flask, Django, pyproject, requirements, package structure

І використовувати цей сигнал у pre-action / loop policy.

## Завдання 5. Не зламати існуючий batching

Після змін має зберегтися:

* підтримка read-only batching
* підтримка multi-action investigation
* але агент має менше ходити по дереву і більше працювати через high-signal entrypoints

## Тести

Додати або оновити тести для таких кейсів:

1. **Kotlin project inspection**

   * модель починає з `settings.gradle.kts` / `build.gradle.kts`
   * не з серії глибоких `list_directory`

2. **Python project inspection**

   * модель починає з `pyproject.toml` / `requirements.txt` / `setup.py`

3. **Invalid list_directory without path**

   * повертається recoverable validation error
   * root listing не виконується

4. **Batch of list_directory with one invalid item**

   * invalid item блокується з точним error message
   * не повинно тихо йти в root

5. **Repeated root exploration**

   * policy/recovery штовхає до `search_files` / `search_content`

6. **Backward compatibility**

   * нормальний targeted `list_directory(path="desktop-app/src/main")` працює як раніше

## Очікуваний результат

Після змін агент при огляді Kotlin і Python проектів має:

* швидше виходити на корисні точки входу
* менше витрачати кроків на directory walking
* не спалювати read-only батчі на root fallback
* частіше використовувати `search_files` і `search_content`
* давати кращі рекомендації на основі змістового, а не механічного огляду структури
